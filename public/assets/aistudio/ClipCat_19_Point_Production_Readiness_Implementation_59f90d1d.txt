1. PRIVACY POLICY PAGE
Create a responsive Privacy Policy that accurately explains information processed; local video/audio processing; browser and local storage; product analytics and diagnostics; error/crash reporting; collected events; excluded information; third-party providers if used; cookies and similar technologies if used; retention/deletion; user controls; future backend handling clearly marked as planned; and configured contact details. Do not invent legal details, addresses, contacts or certifications.

2. TERMS AND CONDITIONS PAGE
Cover acceptable use; user responsibility for video ownership and rights; copyright/IP; uploaded or linked content; local processing limitations; availability and technical limitations; export responsibility; third-party services/dependencies; prohibited abuse; appropriate disclaimers/liability limitations; changes; and configured contact information. Do not invent legal entity details. Mark draft legal text as requiring legal review before public commercial release.

3. REMOVE FRONTEND-EXPOSED SECRETS
Inspect source and production build for API keys, private tokens, passwords, credentials, signing keys, privileged secrets, internal endpoints and sensitive environment variables. Check .env files, VITE_ and equivalent browser-exposed variables, bundled JS, source maps, config and Git ignore rules. Never put private credentials in frontend code; only public config may be exposed. Redact discovered secrets and recommend rotation; never test them against live services.

4. HTTPS CONFIGURATION
Prepare secure HTTPS deployment. Inspect hosting config, redirects, mixed content, asset loading, API URL and deployment settings. Public production deployments must use HTTPS; redirect HTTP where supported; avoid mixed content and hardcoded HTTP production API endpoints. Keep localhost development working; do not force HTTPS on localhost in a way that breaks it. Document domain/hosting-dependent work.

5. COOKIE CONSENT MANAGEMENT
Inspect actual cookies, analytics technologies and tracking. Implement accessible consent management where required: explain tracking, distinguish necessary storage from optional analytics, offer appropriate accept/reject/customize controls, do not load optional tracking before required consent, allow preference changes, persist choices appropriately, avoid repeated banners after valid choice, and support accessibility/responsiveness. Do not invent cookie usage. If no cookies requiring consent exist, do not falsely claim they do. Apply relevant requirements; a banner is not a substitute for a privacy policy.

6. META TITLES AND DESCRIPTIONS
Add unique titles and descriptions for relevant routes, correct language, canonical URLs only when real, Open Graph and Twitter/X metadata, and correct app branding. Do not invent canonical domains. Configure non-indexable routes appropriately.

7. SOCIAL PREVIEW IMAGE
Prepare a branded ClipCat Open Graph image using official mascot/brand assets. Include ClipCat name, AI video clipping positioning and official purple/lavender identity. Recommended 1200x630. Save in public assets and connect metadata. Do not stretch logos or use unrelated mascots.

8. CUSTOM FAVICON
Use official ClipCat mascot icon. Prepare suitable favicon formats/sizes and update HTML references, Apple touch icon where applicable, manifest icons where applicable and application branding. Preserve proportions.

9. SITEMAP AND ROBOTS.TXT
Prepare for public deployment using only real configured production URLs. Do not invent a domain, include private app routes, expose diagnostics/project data/private paths, or index private/local-only content. Configure robots directives and dynamic generation if needed. If domain is unknown, make configuration explicit and document it.

10. IMAGE ALT TEXT
Audit all images. Add meaningful alt text to mascot, SDP/product logos, informative illustrations and thumbnails where appropriate. Decorative images should use empty alt text where appropriate. Avoid repetitive/meaningless descriptions and sensitive data in alt text.

11. IMAGE COMPRESSION AND OPTIMIZATION
Optimize mascot, SDP/product logos, icons, illustrations, thumbnails and social preview images. Use WebP/AVIF where supported with suitable fallbacks; avoid oversized assets; specify dimensions to prevent layout shifts; lazy-load offscreen images but not critical above-the-fold branding; preserve quality and logo proportions. 13. COLOR CONTRAST AND ACCESSIBILITY

17. FORM VALIDATION
Audit project names, video URLs, file selection, caption settings, templates, application settings, search and support forms if present. 18. SPAM AND BOT PROTECTION
Prepare protection for public forms and future backend endpoints. Frontend: prevent accidental duplicate submissions, clear states and usability throttling; do not rely on hidden fields for security. Backend requirements: rate limiting, request validation, abuse detection, CAPTCHA/challenge only where justified, IP/user limits where applicable, safe errors and monitoring. Do not add intrusive CAPTCHA to ordinary local workflows. Backend enforcement remains pending while no backend is connected.

19. PRODUCT ANALYTICS AND ERROR TRACKING
IMPORTANT: ClipCat WILL USE ANALYTICS to understand application usage, identify failures, diagnose errors and improve reliability. This is not a zero-analytics product.

A. Analytics objectives: feature and navigation usage; project creation funnel; upload outcomes; processing stage outcomes/failures; backend connection failures; export outcomes; app errors and unhandled exceptions; frontend performance indicators; browser/app version compatibility; error frequency and affected versions.

Example events: app_opened, page_viewed, project_creation_started, project_creation_completed, upload_started, upload_validation_failed, processing_started, processing_stage_completed, processing_failed, export_started, export_completed, export_failed, api_connection_failed, settings_updated, application_error, unhandled_exception. These examples do not authorize arbitrary collection.

B. NEVER collect/transmit: video/audio content, frames/screenshots of user content, transcripts, captions, notes, project names, original filenames, local filesystem paths, full private URLs, API keys, access tokens, passwords, credentials, personal information, sensitive form values, raw request/response bodies, browser storage contents, clipboard contents, keystrokes or session replay recordings by default.

C. Error diagnostics may include sanitized error category/message/stack, app version, browser/OS/platform where appropriate, route identifier without sensitive query parameters, processing stage, timestamp, correlation/event ID and non-sensitive technical metadata. Sanitize query strings, fragments, local paths, filenames, user-entered values, tokens, credentials and exception messages before transmission. Never assume exception messages or stack traces are safe.

D. Architecture: inspect/reuse suitable existing provider if present. Otherwise create provider-independent analytics abstraction, strict event schema, event validation, centralized sanitization, explicit configuration, and keep analytics disabled if no valid provider configuration exists. Document recommended provider/setup. Prefer privacy-conscious free-tier or self-hostable options where practical. Do not introduce paid services without approval or invent keys. Suggested modules: analytics client, event definitions, sanitization, error adapter, consent integration where required and environment configuration.

E. Consent: coordinate with cookie/consent implementation. Do not initialize optional tracking before required consent. Respect choices and applicable requirements. Do not claim cookies are used if provider does not use them. Allow preference revision where applicable.

F. Verify expected events, payload exclusion, URL/error sanitization, no raw video/transcript data, offline resilience, analytics failure not breaking app, duplicate control, no requests when disabled, and correct development/production configuration. Include sample sanitized payloads in docs. No session replay or keystroke/content-level recording.

G. Update privacy statements. Remove inaccurate claim “Zero personal data, telemetry, or analytics collected.” Replace with a truthful explanation of limited usage analytics and sanitized technical diagnostics, excluding user-generated media and sensitive content. Claims must match implementation.
